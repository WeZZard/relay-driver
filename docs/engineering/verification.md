# Verification contracts

This catalog registers the proof required by the design. It contains no execution results. Store actual logs, recordings, and human review outside the tracked design tree and reference the relevant IDs from their reports.

| ID | Contract | Required proof |
| --- | --- | --- |
| INPUT-01 | Ordinary interactions use the intended input path. | Inspect backend dispatch and exercise a visible control whose pointer or keyboard behavior is the subject; distinguish target discovery from activation. |
| INPUT-02 | Accessibility actions are confined to identified accessibility tests. | Exercise direct activation or value-setting in that mode, retain its label, and verify that ordinary interaction claims do not inherit its success. |
| EXECUTION-01 | SSH submission and uploaded-script execution satisfy the same event and timing contract. | Run the same input, observation, and failure sequence through both paths, including code streamed through SSH and uploaded JavaScript, TypeScript, and Python scripts. Verify individual receipts, parent execution identity, deployed script identity, remote timing, recording references, and preserved outcomes. Introduce transport delay, a disconnect after admission, and startup failure after resource acquisition; recover from a replacement host through persisted/discoverable identities, verify that event times do not shift to host request times, and ensure recovery does not replay the action. Equivalent semantics are required, not identical durations. |
| SCRIPT-01 | Generated-code actions have individual coverage. | Exercise actions in loops and conditional branches plus a failure through JavaScript, TypeScript, and Python SDKs; compare receipt semantics and original failure propagation. Verify that handle creation does not claim execution, a second call cannot dispatch, recovered handles cannot replay, and a deliberate retry has a new linked identity. Exercise native success/failure with retained/failed evidence, mandatory scope-exit checking, and combined failures without masking the backend exception. Demonstrate how an opaque script or bypass limits coverage, and distinguish a CLI process interval from its inner actions. |
| TIME-01 | Events map to the actual recorded media timeline. | Correlate known input and captured frames through encoding, export, seeking, and any derivative for both execution paths; report measured uncertainty. Distinguish recorded operation intervals from any measured input-dispatch timestamps and reject missing or invalid clock mappings as precise evidence. |
| TIME-02 | Observation uncertainty and provenance remain honest. | Inspect sparse observations and later annotations; verify interval retention, frame references, and the distinction between visible and nonvisual evidence. |
| CAPTURE-01 | Recording loss stops further walkthrough input. | Interrupt capture between SSH commands and during a multi-action uploaded script; verify that the next input is refused in each path and inspect the incomplete attempt and separately identified continuation. Interrupt the explicit continuation's phases, recover them without duplicate attempts, and verify fresh timing/readiness and refusal from stale handles. Account for already admitted or queued input rather than claiming that terminating the SSH client stops it. |
| RESOURCE-01 | Remote resource limits preserve available evidence through exhaustion. | Through both execution paths, disconnect during output flooding under deliberately small task/output/buffer limits. Exercise concurrent producers, bursts between samples, unrelated volume consumption, stalled supervision, deadline expiry, and failed finalization. Verify atomic byte reservations, bounded Relay buffers/output, refusal before ordinary use consumes shutdown capacity, explicit truncation/damage, and an inspectable exported package. Measure recorder growth and shutdown demand; distinguish watched thresholds from environment-enforced quotas. |
| EVIDENCE-01 | Package references and original evidence remain intact. | Check hashes, decoding, missing references, corrupt artifacts, and derivative mappings. Verify delivery of an explicitly damaged original beside a playable continuation while preserving failed playback and incomplete coverage. Missing bytes, transfer corruption, invalid references, or failure to decode media advertised as playable must fail acceptance. Verify that late enrichment creates a revalidated package revision without changing original evidence. |
| EXPORT-01 | Evidence survives environment teardown. | Accept the package on the host, relinquish the test environment through its governing workflow, and open the package locally. |
| SNAP-01 | Capture readiness is screenshot capability, not recording. | Refuse input when display screenshots are unavailable (driver call fails) and admit when they succeed; verify the refusal diagnostic names screenshot capability; verify no recording-state probe gates admission. |
| SNAP-02 | Every event carries a dispatch-time before/after causal pair. | For real GUI events, verify the before-snapshot precedes dispatch, the after-snapshot is captured exactly the declared agent-supplied interval after dispatch completion (declared interval and actual capture times journaled), files sort chronologically by name, hashes match capture-time provenance, and a missing interval is refused before dispatch with no default. Near-identical frames are acceptable; deduplication never occurs. |
| SNAP-03 | Coalescing groups are sender-declared and preserve per-event journals. | Declare a typing group; verify one before/after pair spans the group, every keystroke remains its own journal event citing the group identity, group integrity checks refuse a group lacking exactly one before/after pair, and grouping is never inferred. |
| SNAP-04 | Snapshots survive delivery as verified package artifacts. | Deliver a package with snapshot pairs and an application-supplied attachment; verify hash integrity, dispatch-captured provenance, group-pair consistency, and that the viewer renders before/after pairs per step without any video. |
| REVIEW-01 | A reviewer can navigate to the intended behavior. | Select steps, follow stable links, observe synchronized highlighting, and inspect a precise still-frame checkpoint. |
| REVIEW-02 | Attempts and outcome dimensions remain distinct. | Review a failed attempt followed by a retry and confirm that recording completeness, execution outcome, and human judgment remain separate. |

Each backend must establish its own applicable input and timing contract. A passing result for one backend cannot establish another backend's delivery path. User stories reference these IDs through their [index](../user-stories/index.md).

Both execution paths must pass the applicable contracts before their shared recording guarantee is accepted. A successful upload, a clean SSH exit, or one outer script event is insufficient proof.
